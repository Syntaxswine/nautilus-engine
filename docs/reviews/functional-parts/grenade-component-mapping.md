Status: documentation and binding proposal, based on immutable Git objects. No grenade kernel, registry extension, pickup implementation, shared metadata or consumer pin is changed by this report.

These are independent candidate pins: 03 exports parts and c7 exports grenades. Neither pin's package manifest currently supplies both entries. Architect must combine reviewed sources and reconcile public exports, schemas and package closure before a combined installed example is claimed. The component-binding schema described below is proposed, not an existing public 03 API.

## Fixed grenade contract

`GRENADE_COMPONENT.id` and `GRENADE_CONTRACT.id` are `item:grenade`. API, command and state-schema versions are 1. State is `nautilus-grenade-state` v1, URI `urn:nautilus:schema:grenade-state:1`; profile is `farmyard-static-same-plane-v1` v1. Required behavior capability is `nautilus-grenades-static-planar-v1` v1; optional aiming capability is `nautilus-grenade-aim-v1` v1. Use `grenadeRequirements(state)` / `assertGrenadeCompatible(state,consumer)` and the corresponding parts requirements separately; the existing requirements envelopes each name one schema.

The reviewed profile supplies the 33-point authored arc, 97-point wall/fog footprint, 10 m range, 5 m blast and 120 raw base damage. Equipped pistol, pistol-offhand or SMG costs 2.5 AP; other supported weapons cost 5. Command-time execution spends one grenade, synchronizes matching grenade-pack rounds and stages ordinary damage, casualty, guard, sight/fog and control effects. There is no fuse or authoritative flight state. **Ordinary execution consumes no RNG.** Host RNG remains unchanged, host-owned save data; a seed/stream is not an input port for this profile.

## What discovery and placement should bring

Retain the 03 structural envelope. It supports slab, solid, wall, door and stairs; its typed connections are door-aperture/stair-from/stair-to, and its initial overrides are door settings. Item/stock/component fields require a separately versioned generic component bundle and preparation step. A solid or empty assembly is insufficient to implement a grenade item.

| Binding responsibility | Concrete data or required retained service |
| --- | --- |
| Definition/discovery | `item:grenade`, exact content version/hash and c7 provider pin, fixed profile/capability, public guide and native art/socket references. Register the reviewed provider once; saves select known content, never executable scripts. |
| Authoring seed | Stable instance/local-stock key, explicit `loadout` or `world-stock` recipe, bounded integer initial quantity, actor reference or supported world anchor, functional/decorative intent and source paths. These are proposed component fields, not additions to a strict 03 record. |
| Native placement | Inherit translation and quarter turns; resolve exact floor/support and a native anchor. A 03 world `content` entity can hold content ID/version and position, but automatic assembly-relative item emission and inventory behavior still require the generic binding work. |
| Atomic adoption | Required `atomic-grenade-context-commit-v1` capability, version 1: compare the complete relevant host projection and old serialized sidecar; persist accepted sidecar/resource/ordinary consequence changes together. Preserve unrelated full host fields. |
| Visibility/control | Required `farmyard-visibility-refresh-v1`, version 1: synchronize staged `world.seen`, `visible`, `fogAt`, `control.detected`, phase/engagement and accepted actor facts into retained queues, indices and views. |
| Bodies/loot | Required `farmyard-body-registration-v1`, version 1: register the accepted ordinary casualties once in the complete host body/loot registry. Apply final staged HP/AP/casualty fields; do not apply damage or resistance a second time. |
| Stock/pickup | Loadout initialization is a new-session grant. World stock requires a separately implemented inventory/pickup/capacity/ownership binding. The grenade facade supplies throws over actor stock, not general pickup/transfer semantics. |
| Optional presentation | `GrenadeAim`, `screenToGround`, `FIELD_CAMERA`, `grenadeCameraFrame`; retained input/camera and Artist/UI's reviewed native presentation. Consume newly committed `presentation` and consequences once; cancellation only clears aim. |

The three named host-service requirements are negotiated as capability versions. Their declarations do not install callbacks or create a module-planner implementation. A composition adapter may expose matching services through `./runtime` after their actual interfaces and ownership are implemented. Missing required bindings leave preparation incomplete.

Farmyard's `FARMYARD_GRENADE_PROFILE.initialStock` is 3 for its explicit utility/loadout recipe. Keep that separate from broader parts stock. A single world-grenade pickup can provisionally default to quantity 1; a designer-authored stack needs its own validated quantity. Placement itself never adds ammunition to an arbitrary actor. Runtime `actors[].grenades` and `grenadePackRounds` are current inventory projection; restore/checkpoint adoption never substitutes initial stock or repairs spent resources.

## Identity, copy and complete saves

Use 03 `partIdentity(instanceId,'attachment','stock')` as the stable component binding reference. Its source limits remain 24 characters per instance key and 32 per local key. **Do not universally pass that generated ID into grenade state:** parts IDs can exceed the grenade string-ID limit of 64 characters. Grenade IDs also accept safe integers; preserve number/string distinctions. Persist an explicit collision-free mapping between parts bindings/actor IDs, retained host IDs and allocated short grenade-sidecar/actor IDs. No truncation, coercion or unsupported extra fields inside either strict state envelope.

Use a shared authoritative grenade sidecar for the adopted context and provider, rather than creating a new journal for each placed grenade or actor. Moving a geometry-empty 03 assembly can leave `scene.id` unchanged: its transform emits no settled geometry. The proposed component-bundle identity must therefore cover the parts scene ID, exact component locks/profile, resolved anchors, stock seeds, owner references and ID map. Source array indices or revision counters alone are insufficient.

Authoring copy allocates fresh instance/binding/initial-grant identities, remaps internal references, and explicitly retains or clears external owner links. A copied recipe starts from its authored seed, not the live remaining stock or old receipts. Delete/move/copy is one Editor transaction over structural and component authoring data; it stages a new bundle/session or reviewed migration instead of silently rewriting a live save. Load preserves current IDs, quantities and ownership.

Save the full grenade sidecar, host inventory/actors/control/visibility/body facts, component identity/ID map and parts runtime in one host-owned checkpoint. Validate `openGrenadeState` and `openPartsRuntime` plus the game's schemas before any adoption. The 03 `hostData` field carries opaque data and does not validate grenade semantics; its 1,000,000-byte sublimit can be smaller than a valid grenade state. A larger complete save needs a deliberately specified host envelope referencing both validated states, with its own aggregate budget. The 03 parts journal only accepts interact/walk/advance and event claims; grenade commands keep their own durable journal.

## Preview, context adoption and commit sequence

1. At a grenade boundary, derive the complete current relevant context. For the pinned Farmyard host, use `projectFarmyardGrenadeContext(source,{geometry,bounds?})` over complete current geometry. Preserve source actor order and IDs, sight inputs, damaged/spent resources, equipped weapon, grenade stock/pack rounds, guard facts, world bounds/grid/fog and control. No crop or omitted obstacle is a valid projection. A generic 03-world adapter is still future work; an upright-mover sweep is not a replacement for the reviewed grenade geometry filters.
2. Compare with `matchesGrenadeContext(sidecar,projection)`. Only a relevant change requires `adoptGrenadeContext(sidecar,{version:1,id,expectedRevision,...projection})`; do not record checkpoints on render frames, every movement tick or unchanged previews. This avoids consuming the finite journal for irrelevant activity.
3. A context checkpoint intentionally replaces stale projected data. Its `expected.context` describes the **old sidecar** context. Guard its old `expected.state` and the captured **new host projection** under the host transaction; verify the proposed `next` matches that still-current projection. Requiring the already-changed host to match the old context would prevent legitimate checkpoint adoption. Do not overwrite newer host injury/equipment/geometry changes if the captured projection became stale.
4. Preview/stage a throw with `{version:1,id,expectedRevision,actorId,point}` through `previewGrenade` / `stageGrenade`. Before a new throw commit, compare stored serialization to `expected.state` and freshly projected host data to `expected.context`; reject/reproject on mismatch. Adopt the accepted final actor/resource/control/world projection and sidecar atomically. Dispatch newly accepted ordinary consequences and transient presentation once after commit.

The ordinary sight/fog/control and engagement/AP refresh is already staged in `next`. The host must not run another AP-granting engagement transition or re-award AP after adoption. The source's accepted engagement policy can refill on entering player combat before debit; this is a command consequence, not load/checkpoint behavior. A repeated exact command returns its old receipt and the **current** `next`, with `repeated:true`, no new presentation and no consequences. Changed payload/kind under an old ID rejects. Loading also emits no effects.

Throws and context checkpoints share one 128-record ID namespace. The entire grenade state also has joint limits of 8,000,000 UTF-8 bytes, 500,000 plain-data nodes and depth 24. Prospective aggregate limits can stop a command before record 128. No eviction, journal reset, or replacement sidecar may clear accepted IDs to make the same live session spend again. No approved archival/compaction policy is supplied by c7; surface a named capacity refusal and preserve the accepted checkpoint.

## Readiness limits and next assignment

The c7 profile requires explicit false support flags for windows, fueled targets, volatile targets, fire and multilevel context. Known reactive fields and window/glass geometry also reject. Additional host capabilities cannot enable those features within this fixed profile: they require a separately reviewed future profile. There is no RNG/detonation port to bind here. Do not flatten 2.12 m upper floors, stair traversal, window openings, tank chains or active fires into the ordinary ground-plane projection. Actor layer is `z:0`; trajectory `z` is metre height above that plane, while parts uses metric `h`. Conversion and supported scene selection must be explicit.

Architect can assign a generic component-bundle/identity and retained-context adapter after combining the pins. Editor then exposes ordinary discovery/loadout choices and broader stock only when its inventory binding exists; UI consumes the public aim/presentation contract; Artist supplies measured native art/rig evidence. Required next proof: installed combined exports; missing-service/profile refusal; new-session loadout 3 versus world stock; atomic source-equivalent refresh with no double AP grant; changed host-context adoption; exact retry after later injury; save/reload without refill/replay; and journal/node/byte-capacity refusal. This documentation does not claim those combined workflows are implemented.

Recommendation: retain the fixed ordinary Farmyard profile for its named adoption. **Accuracy:** code inspection shows the source abstraction and explicit refused features, without physical ballistic calibration. **Efficiency:** the bounded headless path and boundary-only context adoption are the intended policy; no speedup or integrated frame-rate measurement is claimed. **Narrative:** existing stock, AP discounts, allied/self damage and guard consequences preserve Farmyard's authored tactical experience. Richer geometry, fuel/fire and window behavior retain their separate future profile requirements.

Evidence for this mapping is source inspection of the two full commits above, including `GRENADE_COMPONENT`, `GRENADE_CONTRACT`, model/ID validators, state staging/adoption/requirements and the pinned guide. The existing 03 read-only probes established item-field refusal and the empty-assembly identity gap. Grenade runtime/conformance acceptance remains with the fixed c7 candidate; this doc change does not import or execute another kernel.
