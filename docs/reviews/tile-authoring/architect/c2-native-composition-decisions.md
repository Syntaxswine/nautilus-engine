# Native ownership in the combined tile workshop

Architect decisions, 2026-11-02. These are requirements for integration, not an acceptance record. The Artist's `a3505278b4e67c1b57d0ebb1469cdc8bbbfa82f6` is a development reference; independent review returned a world-transform/currentness defect for correction.

## One manager and deferred construction

The paired Artist owner constructs the actual existing C1 view manager. The session must adopt that exact manager at its original construction site, after same-ID cold reconciliation. A source-authenticated constructor or membership seam must verify it. A second session manager surrounding the Artist manager is not acceptable. The full target document, public projection and finish choice must reach its acquisition through a one-use attempt-owned association, not a global last-document variable or inferred mesh data.

Imports remain inert. Start the actual counted bootstrap before codec and authority work, reconcile an original pending operation before allocating a native context, then create one instrumented renderer/context and manager. Preserve an unresolved bootstrap's original retry handle. The private branch uses the original public tiles namespace; the C1 example's measurement wrapper is not that namespace. Ground/grid decorations are omitted until an actual charged owner exists for them.

## Complete native inventory

Actual provider facts include `color`, `tileField` and `parameterTangent` attributes in addition to position, normal, UV and index. Constructor observations also include four CPU default upload stores (16 bytes) and nine non-sampled API store parts (36 bytes), including cube, 3D and array defaults. These are component observations, not physical-memory measurements.

Use an explicitly versioned private inventory contract that represents those facts completely. Preserve the frozen appearance and strict contracts as compatibility references; do not silently widen their schema, omit attributes, relabel geometry or pretend non-2D default stores are sampled 2D pages. All fifteen resource limits and the normalized-work ceiling remain unchanged. Geometry CPU/API stores retain their conservative derived-allocation charge. Prepared and final consumers must authenticate actual source-issued observation capabilities, not copied inventory JSON.

## Release acknowledgment

The original C1 manager retains an unverified retiring record. A later positive native release needs a closure-private continuation in that same manager, bound to its exact original record, view, one-use handle and actual disposal result. The continuation must reuse the manager's own release/unlink checks. No external mutation of the record set, diagnostic zero or unrelated receipt grants release.

A complete historical release can remain valid after context end when it still names the same already-released allocations and exact original receipt. It grants no live resource, admission or upload permission. Requiring a live context solely to acknowledge that historical release could strand cleanup. Unknown, unreleased and new-generation resources cannot borrow it. Retain unknown resources until their actual release is proved.

## Resource loading and UI ownership

Selection does not fetch or import artwork. An explicit load action acquires the actual selected encoded bytes and prepares its resident palette page through bounded resource work, with zero editing credit and no IDs, import or WAL write. A later real command pays its own source, copy, plan and native work. Unverified cancellation retains debt; a new owner cannot erase it.

Rectangle and overlay controls share one actual UI coordinator and service. Attachment fan-out must preserve full source/currentness checks and invalidate actions when callbacks detach, rebind or dispose their connection. The C1 default mount stays compatible. Agent canonical commands remain independent of DOM form provenance.

These choices favor accurate source and ownership accounting, reuse the existing session/manager rather than duplicate state, and provide a coherent authoring workflow. Efficiency claims here are code-based expectations, not frame-rate or total-RAM measurements. Native, combined workflow, recovery, save/reload and cleanup still require direct acceptance evidence.
