# Browser-owned appearance accounting: Architect review draft

**Proposal only; no runtime or adoption approval.** Prefer a separate `nautilus-browser-owned-appearance-accounting@1` profile for the browser editor. Preserve the existing strict physical-accounting profile, its closed DTOs and its ceilings unchanged. Strict remains unavailable on an ordinary browser unless a genuine platform owner supplies its required physical-copy/reclamation proofs. Never fall back between these profiles.

## Feasibility and preference

Fixed Artist `f029e7e75e225c5f973052552deb61403a2fc915` correctly identifies the gap in `CAPTURE-UPLOAD-PROPOSAL.md:19–40`: WebGL storage dimensions, `BUFFER_SIZE`, live native identities, `gl.finish` and deletion observations do not bound opaque browser/driver copies, physical VRAM or GC reclamation. Its conservative unverified root/material debt also prevents indefinite replacement under two roots. More probing cannot supply these missing capabilities.

Use one **new, engine-owned WebGL2 context**, the existing pinned shared Three, a fixed bounded image/data pool, independently owned source/candidate public-provider geometry, and an instrumented owner installed at context construction. Extend the existing new-context buffer observation seam; do not patch a user's shared renderer. Keep strict and browser ledgers in separate owner lifetimes. Do not import a strict ledger and relabel or forgive its debt.

| Criterion | Assessment and preference |
| --- | --- |
| Accuracy | Strict physical accounting makes a stronger claim but is unavailable here. The proposed browser profile accurately describes observable engine ownership and API-logical stores while declaring all opaque storage UNMEASURED. Prefer this narrower, explicit claim for a browser editor; it is neither bounded total RAM nor a physical VRAM model. |
| Efficiency | From code inspection, serial reuse of the fixed scratch/output buffers and two original textures avoids per-edit image copies. Releasing replaced views from engine ownership permits repeated edits within two roots. These are estimates, not new timings or proof of driver memory stability. Existing fixed diagnostic numbers belong to the old diagnostic profile and cannot be reused as measurements of this proposal. |
| Narrative | Subjective preference: repeatable paint/clear/Undo/Redo with explicit “resource busy/debt” refusals suits map authoring better than a preview that can never replace its second root. Keep existing clean finish-only rendering available. No game, mobile performance or higher physical-memory guarantee follows. |

`profile.json` defines the proposed observable scopes and unchanged numeric ceilings. `contracts.json` describes closed ephemeral records and ports; it is a review specification, not a runnable JSON Schema. `references.json` authenticates the source used for this design.

## What the totals mean

- Count **actual engine-held fixed, non-shared ArrayBuffer backing capacities** once per real backing identity, regardless of subviews. Equal bytes/hashes never merge separate buffers. Fixed/non-shared is the initial supported profile; refuse SharedArrayBuffer, resizable/growable or unknown-capacity stores. Hash input, decoded output, caller window, scratch, snapshots, upload copies and idle caches all count in their own immutable buckets. A transferred store changes owner; it is not free while the receiver is an engine owner.
- Count each logical API texture allocation by actual native handle/context/epoch and complete storage layout, including mip levels. Count logical buffer storage from actual owned `bufferData`/`BUFFER_SIZE` observations. These are API-store sizes, **not measured driver memory**. Count acquiring reservations before calls that can allocate, and reconcile them to the actual handle without counting a reservation plus its single fulfillment twice. Independent copies remain independent rows.
- The **32MiB additional decoded limit** covers additional image/decode/scratch/application-upload backing capacities, additional API-logical image texture stores, and unfulfilled declared application reservations. The **4MiB derived limit** similarly covers derived CPU capacities, logical derived data textures and application-derived reservations. Geometry CPU/API stores are separately enumerated and constrained by the exact public geometry profile and root/triangle/cell limits; neither geometry nor encoded bytes is reported as zero/free. The existing 64MiB encoded-owner ceiling is retained as a separate scope, not called decoded RAM.
- Count **four actual sampled allocation/context/epoch tuples**, including borrowed base, both artwork pages and sparse data. Reservations for possible new sampled objects also consume headroom before allocation. One actual handle shared through owner-attested aliases counts once. Same asset/dimensions/Three Source does not prove sharing. An update that could replace a handle needs peak capacity or must refuse; do not discover a fifth object only after overspending.
- A constructor-frozen baseline inventory may identify the already borrowed base atlas and its logical mip storage as `baseline-visible`. It still consumes a sampled slot and is separately reported. Additional copies/new base objects cannot be reclassified as baseline. The existing HTML-image decode backing is opaque browser storage, explicitly UNMEASURED; every actual application-owned buffer obtained from it must be charged. Changing the baseline or accounting profile requires a fresh owner lifetime/context binding, not restamping an in-flight source.
- `opaque` is a required closed record with literal status **UNMEASURED**, explicit excluded categories and `totalRamBoundClaim:false`, `physicalVramBoundClaim:false`, `gcReclamationClaim:false`. It contains no fabricated byte value or nominal “one hidden copy” upper bound. Known application reservations remain charged. A nominal diagnostic reserve is not transformed into a physical proof; a new browser session must start with its own declared scope.

Keep every source, candidate, history, redo, pending, export and idle-cache ownership reference. These are references to actual stores/objects, not a reason string. Counts include acquiring, idle and release-pending debt. Immutable private admission facts drive totals. Observation DTOs are detached; changing a row cannot change category, capacity, sampled identity or retirement. This directly addresses the fixed-f029 quota-row finding.

## Positive logical release, without a physical reclamation claim

Release is a live owner operation over an intrinsic lease, never a caller `verified` flag. An owner can attest that a store/object is no longer held by the defined engine ownership scope; it cannot attest that a browser or GPU driver has physically reclaimed it.

1. Inspect all registered source/candidate/history/redo/pending/export/cache and borrowed references. Any reference, active use, uncertain adoption or partial ownership keeps its debt charged. Revoke the specific lease; do not dispose a borrowed atlas/base/material or another view's buffers.
2. For CPU ownership, either verify actual detachment and no engine-owned receiver, or remove all engine-owned strong references after every borrowing lease is returned. The latter is an audited `engine-owner-release` claim, not JS reachability or a GC claim. Caches, diagnostic records, closures, Three source/image fields and output views belong in that audit. Do not keep the disposed root/arrays in a hidden retained set and call them released. An external alias requires an explicit borrow lease or makes ownership release unavailable.
3. For native textures/buffers, observe deletion/invalidity of the exact object in the original current context/epoch after supported disposal. Complete geometry/material/scene/render-list ownership release is also required. `.dispose()` alone is insufficient. Context loss has a separate `context-lifetime-ended` receipt: it invalidates logical API stores and all old handles, without proving physical reclamation; it cannot authorize an old request in a new epoch.
4. Only the owner may issue a closed logical-release receipt and update its private facts. Unverified/failed releases remain charged; source/error/debt stays visible. Never label this `physical-retired-verified`, and do not feed it to strict physical DTOs.

The fixed runtime's retained roots, public native records, material maps, rows and closure ownership do not implement this release contract. It is a real implementation prerequisite. The existing index/drawRange currentness omission must also be fixed, with an exhaustive supported-state predicate or refusal of unsupported state; this proposal grants no waiver.

## Repeated edits, history and unknown outcomes

Keep one accepted root plus at most one candidate. Complete immutable documents and encoded resource leases serve history/redo; history does not retain an unbounded series of live roots/materials/decoded copies. Reconstruct a history target through the same bounded preparation and whole-document transaction. A history/export/pending owner that actually retains a native object must appear in the ledger and can block the next edit. Do not prune unused saved definitions/versions or normalize retained source to fit a quota; a refusal leaves the complete source/history/redo unchanged.

For paint/clear: capture current source → pure plan → capacity-only bound → reserve/prepare/warm actual candidate → admit only this request's exact owned additions → final pure bind → real history/WAL validation → guarded Review → final live CAS. Preserve the original public Expected. An internally admitted owned delta is not a new Expected or blanket resource mutation allowance. Foreign allocation/release ABA refuses even when totals return to their old values.

After known commit and successful controlled activation, logically release the replaced view only when its live owners are finished. Before commit/refusal, release only the proved unadopted candidate. A failed logical retirement keeps both-root/material/buffer debt and the next preparation refuses at the same caps. Postcommit display errors remain committed-with-display-debt and retry presentation under fresh guards; they do not replay the command.

Unknown acknowledgement freezes writes and retains source + candidate + encoded/history/redo/pending/export union with the original request ID. No speculative release, command replay or reprepare settles it. Same-ID recovery reads the existing authoritative outcome first. Cold reopen preserves the complete v3/checkpoint/journal and encoded obligations; old native handles are invalid, a fresh logical owner lifetime reconstructs only after recovery permits it. Never restore native-ledger permission from a saved DTO.

For repeatability, current ledger rows cover live/debt objects with the existing 1024-row ceiling; immutable IDs/lifetime counters never recycle. Released observations can leave the current table only after all live request/recovery leases settle. Keep bounded release metadata/transition evidence, not an ever-growing strongly referenced native-object tombstone list. Snapshot/event bounds must remain within existing input/node/work limits; overflow refuses. Every owner mutation increments a monotonic mutation epoch, including allocate/release ABA. A bounded log does not erase that epoch or active debt.

## Versioning and binding

No C0/v3 document, artwork, decoration, resource-ref, saved Operation, Review or checkpoint grammar changes. Keep the exact existing nineteen Bindings fields. New browser source/prepared/recovery/retirement records have **new kind names and version1**, a new browser Host/ledger profile, exact `accountingScope:'engine-owned-and-api-logical-only'` and `profileDigest` discriminators, and new ownership-release semantics. The strict SourceCapture@1/PreparedCapture@1/CapacityBound@1/Plan@2 path remains exact and explicitly rejects them.

Use **BrowserAppearancePlan@1**, kind `nautilus-tile-authoring-browser-appearance-plan`, and **BrowserCapacityBound@1**, kind `nautilus-tile-authoring-browser-capacity-bound`. Both require the exact browser `accountingScope` and `profileDigest`. Strict Plan@2/Capacity@1 and Core's future combined Plan@3 are untouched; these browser kinds are not aliases or new versions of either. New browser containers inherit applicable closed Origin/Authority/geometry/resource/cost/history shapes; they do not reuse strict PhysicalAllocation or strict retirement semantics. The Core producer must validate these separate shapes and all aggregate/transition equations before final binding. Strict, combined and browser records must refuse each other through explicit kind/profile dispatch, regardless of structural similarity.

Canonical `profileDigest = SHA256(UTF8(canonical-JSON(profile.json)))`, sorted object keys, array order preserved; only explicit fixed profile data enters it. The manifest includes the canonical `contracts.json` digest, so changing release, row or container semantics changes the profile binding too. Compose the existing ephemeral presentation-profile digest from the provider identity/version/source pin plus `accountingProfileDigest`; bind it through current AuthoringContext, original Expected/authority context, source/plan/capacity/prepared/admitted ledger, existing `presentationProfileDigest` and `allocationLedgerDigest` Bindings, and final live CAS. Switching profile/renderer/epoch invalidates outstanding leases and Reviews. These digests bind observations; private owner capability/currentness supplies authority. Negotiation explicitly selects this profile; unknown IDs/digests or mixed strict/browser records refuse.

## Pending end-to-end attempt budget port

Independent Native design review identified another required port: **one actual per-attempt work/input/output meter, or an equivalent owner-enforced reservation/consumption capability, covering the whole attempt**. Begin it before source/history observation or copies. The same owned budget must cover those observations/copies, planning, capacity, decode/upload/native preparation and warm-up, final pure bind, and complete real operation/history/WAL validation. No phase reset, fresh nested allowance or caller-provided `chargedBefore`/cost report may manufacture budget. The meter remains separate from original Expected/authority and cannot authorize a write.

The composed Host must privately bind its attempt ID, exact request/source/profile/limits, and phase reservations. Each component consumes audited work and actual input/output/copy observations through the same live capability, or uses a conservative owner-enforced reservation acquired **before** that work; settling a reservation requires the paired owner's actual consumption evidence. A cost DTO or public-kernel numeric estimate is insufficient. Counters are monotonic within their frozen domains; replay/foreign capability or reservation transfer refuses. Geometry, decoded-capacity and encoded-stream byte domains must remain explicit rather than silently treating every pixel copy as command JSON or giving each phase a new packet allowance. Exact domain equations and all applicable unchanged ceilings need joint Core/Artist/Editor review before freeze.

This port is **PENDING, not implemented or supplied by an invented public Core counter**. Existing pure APIs do not acquire authority by accepting a reported work number. `contracts.json.pendingAttemptBudgetPort` records its owner, coverage and refusal requirements. No browser runtime may advertise this profile until an actual paired meter/reservation path accounts for the real final bind and real-WAL checks as well as renderer work. This design review ran no new runtime, browser or profiling checks.
