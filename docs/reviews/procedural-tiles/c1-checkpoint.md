## Measurements and limits

One foreground measurement pass used Node **v24.15.0**, Windows x64, AMD Ryzen 7
5800X. Across 124 selected cases the median was **9.75 ms**; the largest selected
16-leaf/128-segment workload took **555.39 ms**, **2,864,675 modeled work units**,
and **206,374 actual serialized bytes**, with sixteen interior components. Other
validation commands could be concurrent; there is no isolation/warmup guarantee.
These are measurements of this bounded workload, not mobile/per-frame/renderer
benchmarks. The exact-arithmetic model deliberately refuses larger bit/work or
degeneracy demands rather than guessing.

Code-based cost includes quadratic original segment pairs and additional exact
containment/sector grouping that can be quadratic in emitted boundary size. More
fully, the operation-count estimate is `O(S² + E*(S+R) + B² + sorting)`, with
S original segments, E atomic edges, R graph references and B emitted boundary
spans; rational bit costs are separate. This refines the design-stage estimate,
not a measured complexity claim. All grouping tests are charged to the shared
work bound, so a valid large source may remain unresolved before other ceilings.

Accuracy favors native exact topology with explicit unsupported states; this is
source-value correctness, not physical calibration. Efficiency provisionally favors
one bounded overlay for small authoring graphs, with larger/device measurements
still needed. The narrative preference is subjective: predictable L/H footprints
and courtyards with no accidental bridges suit all three games. C2, curved/ribbon/
section/stair evaluators, meshes and gameplay bindings remain outside this tranche.
