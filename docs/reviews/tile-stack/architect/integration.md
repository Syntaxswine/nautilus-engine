# Stacked tile integration

Status: reviewed source imported on the integration branch; combined Root gates
and current source/build/install matrices are pending. Main promotion follows
those results. This record does not declare consumer adoption or a release.

## Result and boundaries

The map workshop opens the stacked tile workshop in a separate tab. A new
workspace retains its complete original three-layer map beside a canonical v1
tile bundle, explicit fifteen-floor binding, immutable finish catalogue and
stack constraints. It uses the existing transaction, input, history and storage
coordinator with explicit profile hooks. Existing v1 workspaces keep their own
loader and storage namespace.

One Review/Apply creates fifteen aligned 8 × 4 m surfaces with 105 declared
crossings and fourteen locked lower owners. Floor navigation shows at most five
labels. Selected-floor, overview and independently captured cutaway visibility
use actual native elevations; visibility changes do not remove allocations.
The nonuniform profile proves that labels and ordinals do not determine height.

Managed rectangles use the optional public stack planner. New isolated level
line/arc/cubic surfaces and cosmetic edits to their unlocked unmanaged owners
use an ordinary public repair request. Both routes retain one actual public
preparation and commit the complete bundle/constraints target through the same
authority. The isolated route preserves constraints exactly; possible old/new
interactions across all floors refuse under its explicit zero-radius profile.
Targeted geometry edits, ramps, automatic joins, support, traversal and game
export remain unavailable in this reference host.

Four cosmetic families reuse the reviewed engine atlas: brick pavers, stone
flags, timber boards and poured concrete. Physical boundary materials and
source geometry remain separate. The visible surfaces are thin; their declared
reservation intervals do not establish slabs, undersides or structural support.

## Design decision

Accuracy favours explicit native floor/source identities, original controls and
declared clearance. Efficiency favours one repair/coordinator and bounded shared
resources; source/work counts do not establish frame rate. For authoring,
reusable finishes and inspection modes provide useful building tools while
games retain their own simulation and story policies. These choices preserve
compatible formats without claiming that a consumer has adopted the engine.
