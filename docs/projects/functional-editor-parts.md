# Functional editor parts: implementation scope

Implementation authorized by the user on 29 October 2026. Placing a functional part in the editor must bring its behavior and connections with it. A game binds its retained services once; compatible authored parts then use the same standard recipes. Usage guides explain the connection and remaining game choices, while the editor performs the checks it can automate.

This project implements the missing authoring-to-runtime bridge from the [modular blueprint](../engine-blueprint.md) and [component handoff standard](../component-handoffs.md). It is not a claim that existing catalogue buildings are already playable. The architect owns contract decisions, fixed-commit integration and release; the existing helpers own the work packages below.

## First complete proof

Build a small two-story structure in the editor from shared parts: supported floor/wall geometry, a real hinged door and a continuous stair flight through a real upper-floor opening. Use the native 2.12 m kit profile, with explicit stored elevations and a correctly fitted existing character/model. Preserve native model scale; choose an actually fitting opening/actor profile and test an oversized actor's refusal. The kit's 1.65 m door and the candidate default 1.7 m mover are not an acceptable implicit match.

The player can enter through the door, climb both ways, encounter a live obstruction, save while on the stairs and resume after reload. Door appearance, collision and saved state agree. Place another instance at a different position/quarter turn, then another layout using the same parts. Both use the same runtime without branches keyed to building names or manually entered world/door/stair records per placed building.

Use existing reviewed art, paint and animation through public bindings. Prefer the approved bear provider when its measured clearance fits; preserve a compatible existing-actor path if the bear review or physical fit is unsuitable. A debug proxy can aid tests, but it does not satisfy visual acceptance. Artist selects and documents the native reference kit. Audit a suitable existing two-story catalogue design, such as Rowan Family House, for later retrofit; do not invent circulation from a mesh merely to mark it functional.

## Contract and data flow

The working public responsibility is a small optional parts facade. Final package/export/schema identifiers are fixed in Coder's first ABI checkpoint; names in this scope do not create released APIs. Keep pure data/compiler code separate from optional renderer, DOM and host execution. No universal entity framework or event bus is a prerequisite.

| Layer | Required contract |
| --- | --- |
| Part definition | Stable type/content ID and exact version; parameter defaults/bounds; visual resources or procedural recipe; native units/origin/bounds; semantic part, attachment, floor/support and portal identities; behavior profile and requirements; initial-state defaults; source/notices and guide link. |
| Authored instance/assembly | Stable instance ID, exact definition reference, placement transform, validated overrides, child instances and typed internal/external connections. Store the source authoring data and initial conditions; no live renderer objects, callbacks or arbitrary scripts. |
| Pure compiler | Resolve definitions and requirements, validate references and native clearance, then deterministically produce a compatible static world, dynamic interaction records, render bindings and diagnostics. All outputs derive from the same settled recipe and transform. Emit a source map back to authoring instance/part/property paths. |
| Runtime host binding | Bind the selected public query/interaction/render/time/commit providers once. Instantiate only the selected features. Visuals observe the same committed door/traversal state used by queries. Input proposes intent; the host revalidates and atomically commits authoritative records. |
| Runtime checkpoint | Versioned envelope with exact scene/definition/profile requirements, compiled-scene identity, matching world/interaction/mover state and host commit/event identities. Validate the complete staged bundle before replacing live state. Game-owned stats/inventory/clocks/RNG remain with their adapters. |

Place the engine-owned authored contract in a deliberate new schema/envelope. Preserve existing map/block, character and strict world-v1 contracts. Do not add unknown fields to world-v1, weaken the donor validator or encode a bear/door as another supported object. Existing unsupported legacy exports return a preserving refusal with paths and remedies; existing maps without parts retain their behavior. Derive required capabilities from actual contents so an empty consumer declaration cannot bypass them.

Use collision-free bounded generated IDs with stable mappings between instance, local part, surface, portal and presentation. Validate uniqueness and foreign keys. Copying an assembly creates fresh identities and remaps internal connections; external connections are explicitly retained or left unresolved according to a declared copy policy. Loading the same save preserves identities. Never truncate an ID into a collision. Different definition/geometry versions cannot be treated as the same scene solely because revision counters match.

## What automatic wiring must do

- **Doors:** derive the visual leaf/hinge binding, closed/open poses, dynamic collision, interaction target, portal state and initial open/lock settings from the declared door part. Do not duplicate moving leaves as permanent static walls. Check occupants, static obstructions and other leaves under the selected geometry profile. State whether operation uses conservative motion bounds or a richer hinge sweep.
- **Stairs:** derive named floor/support endpoints, continuous route, width/head clearance and presentation from one stair definition. Cut actual wall/slab openings and preserve landing support. The route is an explicit walking-support representation, not a claim that decorative treads alone prove traversal. A blocked route pauses without teleporting or inventing a floor.
- **Assemblies:** place, move, rotate, duplicate and delete child parts and all generated references together. First release supports native translation and quarter turns; unsupported scaling, mirroring, arbitrary rotation, curve or geometry profiles reject explicitly. Recompile/invalidate affected immutable query snapshots after authoring edits and undo/redo. Do not silently edit a running session's geometry underneath saved traversal.
- **Editor defaults:** select a functional recipe with useful defaults and ordinary initial settings. Offer decorative mode explicitly where appropriate. Inspectors expose supported game choices, not raw dependency graphs. Required missing connections prevent entering play/exporting to that profile; authoring may preserve incomplete work with clear diagnostics.
- **Diagnostics:** report stable codes plus instance/part/property path, reason and remedy. Show functional, decorative, incomplete and unsupported status. Clicking a problem selects the affected part. Checks cannot mutate the document or clear history; a failed compilation keeps the last accepted preview/session intact.
- **Presentation:** use host Three and existing content providers. Animate from committed state/events; frame rate, visual failure and animation markers must not create duplicate gameplay effects. Floor visibility is presentation only: offscreen/hidden actors and geometry remain in collision/occupancy. Reuse the five-label floor controller and host-confirmed floor transitions on desktop/phone.

An automatic binding selects known, versioned engine behavior. A save never installs arbitrary code. Games retain policy for keys/permissions, costs/AP, damage, fire, sensory interpretation and missions. Support one bounded geometry/movement profile well before claiming a universal physics/pathfinding service.

## Acceptance for the first increment

- [ ] A headless installed consumer can discover definitions, validate/compile the same authoring document and negotiate requirements without DOM, renderer, storage, clock, network or donor/editor imports. Strict data validation rejects accessors, hidden fields, unsupported values and cross-version input before invocation/copying.
- [ ] Compiler fixtures produce equivalent settled outputs for the same input; translated/quarter-turned instances preserve native geometry, floor elevations, door poses, routes and IDs. Second layout/instance uses the same runtime. No overlapping dynamic/static leaf collision or blocked slab holes are hidden by the visual preview.
- [ ] Actual editor placement and each move/rotate/copy/delete operation is one undo transaction. Undo/redo, save/reload, export/import and failed/late compilation preserve identities, connections, current document and history. Invalid references and unsupported legacy exports report actionable preserving refusal.
- [ ] A closed door blocks the actor; an open door permits the measured opening; locking/unlocking follows a bound policy; occupants, static solids and another leaf prevent unsafe operations. Dynamic collision, portal/query state and the rendered leaf agree after actions and reload.
- [ ] Between preview and commit, change occupancy, permission or expected state for door/stair actions. Applying the stale intent rejects without changing either authoritative record or emitting effects. Replaying an accepted intent cannot repeat the action, cost or presentation event.
- [ ] An actual shared character can approach and climb both ways continuously through the authored stair opening. Oversized/tall bodies reject appropriately. Live/hidden-floor obstructions stop progression; clearing permits resumption. Departure/transition/confirmed arrival use the correct floor identities and existing floor-follow UI.
- [ ] A complete staged runtime save preserves a changed door, actor position and mid-stair distance with exact content/geometry versions. Stale/incompatible/tampered bundles leave the current game intact. Reload does not replay sounds, rewards or commands, reset authored identity, heal or refill actor resources.
- [ ] Real desktop and narrow-phone workflows run through editor build -> validate -> play -> interact -> save -> reload. The reusable title screen starts/continues the prepared scene with reliable focus, pause/input, cancellation and retry. A phone viewport is reported as layout evidence; physical-device performance remains separately measured.
- [ ] Source and offline installed-package examples use the same public contracts/resources and produce matching behavior/presentation. Old maps, all existing placement restrictions and headless entries still pass. Optional/unselected modules remain unloaded.
- [ ] Record loaded/package bytes, representative compile/rebuild time, scene/actor counts, draw calls and named runtime/device evidence. Compare the same workload and label measurements versus estimates; no unmeasured frame-rate or 90-percent-complete claims.
- [ ] Each accepted candidate passes `npm run check`, `npm test`, `npm run test:upstream`, `npm run build` and affected package/browser/visual checks. Track and stop disposable helpers, verify process identity/ports and preserve evidence. Promote only the passing combined result; adopt game pins separately.

## Design decision and review basis

**Accuracy:** prefer explicit semantic parts compiled from the same settled geometry as the art. Source review shows descriptive catalogue openings and world links do not already execute doors/stairs. AABB collision can be exact for authored axis-aligned primitives but is an approximation for curved/sloped/detailed meshes; select a richer provider where that use case needs it.

**Efficiency:** compile at authoring/load boundaries and invalidate changed assemblies; share immutable definitions and lazily load selected content. This is a code-based architectural recommendation, not a measured speed improvement. Preserve small direct-import use cases and measure real workloads before adding caches or further machinery.

**Narrative:** share functional doors/stairs/items while each game owns art selection, cast, permissions, time/cost and consequences. Prefer that boundary for Farmyard, AFT and Tinderbox so automatic wiring does not import another game's story or simulation policy.

Independent source review of UI `25224b9...` found the input-copy/validation ordering, current occupant-only door-operation check and ID-policy seam in package 0; confirm each with tests before fixing. Source inspection also confirms the manually authored reference yard, visual-only prefab lots and native doorway/mover mismatch. Those are observations from code, not a fresh behavioral/performance certification.
