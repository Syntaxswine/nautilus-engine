# Asset-rendering benchmark

`tools/bench-asset-rendering.mjs` measures how fast Nautilus turns assets into renderables and draws them, as an A/B of two engine trees. It was written for the goal of rendering massive structures twice as fast, and it answers round 1 of the [0.8 hostile review](reviews/2026-10-29-hostile-review-0.8-round-1.md) (MF4: there was no valid instrument; the only recorded draw-call figure was 1).

## Modes

| Mode | Host | What it measures |
| --- | --- | --- |
| `--editor` | The built editor (`dist/`) of each tree: roof → prefab → wall → inherited AFT scene | Cold open time; frame time, GPU time and draw calls per pass at an overview, a close view at the first building, a far view at the last and a level-0 cutaway; full-frame pixels with depth-tie masks |
| `--editor --counts-only` | The candidate's built editor alone | Every map's asset draws in each view, culled as its frames draw them and unculled, without rasterising (the WebGL draw calls are no-ops); quick on any backend, so CI runs it |
| default (preview) | The editor's house preview scene (`apps/editor/prefab-preview.js`), source trees | Building build time and frame time without the inherited ground |
| `--diff` | The preview scene of both trees in one page, on SwiftShader | Byte-for-byte frame comparison, with the depth-tie oracle (`--explain`) |
| `--node` | Node, no browser | `createBuildingModel` time per design at game and authoring LOD, plus geometry digests |

The editor mode is the delivered quantity: what an author sees in the workshop. The workloads are round 1's nine maps (w0–w7), round 3's five lamp-lit maps, and round 4's threshold map and lamp maps, regenerated by `tools/bench/workloads.mjs` through the public headless APIs:

| Workload | Content |
| --- | --- |

| w1-32x-largest | 32 copies of the largest design |
| w2-32-distinct-most-meshes | 32 distinct original designs with the most meshes |
| w3-32-distinct-most-triangles | 32 distinct originals with the most triangles |
| w4-32-gross | 32 Gross houses (13 designs) |

| w8-gross-rows-of-8 | 32 Gross houses placed eight of a design side by side: the smallest cluster of neighbours the editor batches (a shelf row's end splits some, which draw per copy) |
| l1, l4, l5b, l6, l7, l8 (…-lamps) | w1, w4, w5b, w6, w7 and w8 lit by six always-lit fires: point lights with shadows (six cube faces each, 30 m range) on the free tiles nearest six points in the lanes, where round 3's review put them |
| l4x-32-gross-18-fires, l4n-32-gross-12-night-lamps, l4s-32-gross-6-spotlights | The Gross houses lit by 18 fires in three lanes, by 12 electric lamps (streetlights and floor lamps) at 22:00, and by six spot lights switched on, where round 4's review put them |

## Method

- **Draw calls.** `renderer.info.autoReset` is off and reset per frame, with the shadow map's `render` wrapped, so a frame counts its shadow pass, main pass and composite. Counts must not change between frames; the probe throws if they do. Every run reduces motion (`prefers-reduced-motion`), so the fires stand still: a fire's flame once added a draw between frames on a lamp-lit map.
- **Frame time.** One synchronous `scene.draw()` and then a one-pixel `readPixels`, so "total" includes the GPU's work; "cpu" is the `draw()` call alone. No inspector is attached while timing (`--profile` is a separate run: it slows the code about fivefold).
- **GPU time.** Where the browser offers `EXT_disjoint_timer_query_webgl2` (headless Edge on ANGLE/D3D11 does), each timed frame is also wrapped in a TIME_ELAPSED query. It spans the frame's first command to its last, idle gaps included, so in a frame the CPU feeds slower than the GPU draws it, the span follows the feed: with the page's CPU throttled ×3 and the same draws, main's assets-only span grew ×4.4 (round 4). Each view's `gpu` entry says, per arm, whether the span exceeds the CPU's submit time (`own`, with no margin: round 5 saw 0.50 ms against 0.49 ms flagged). Only then does the GPU's work show in the span, and even then the span keeps the idle gaps before the GPU fell behind: it bounds the GPU's own time from above, and the span less the submit time bounds it from below. Where both arms are fed slower than they draw, its ratio is the feed's and shows nothing about GPU work. The GPU side of a change is the triangle count and the SwiftShader proxy (below).
- **Pairing.** Both arms run as two pages of one headless Edge. For every map and view, blocks of frames alternate A B B A, seconds apart, and each run reports each arm's median block. The speedup is A/B per run, summarised as the median over runs with its range. Machine drift falls on both arms. The blank map runs identical code in both arms, so its ratio is the noise floor.
- **Open time.** The map's reference blank is opened first (it releases every template and library), then the workload; the arms alternate. Once the scene is open, the editor's `open` fires its floor control, whose `setOptions` starts one more prefab update that `open` does not await. The bench waits for it, outside the open time, wherever the layer keeps it (`pending`).
- **References.** A map's reference is the blank map (no buildings, wall runs or roofs) with the same props: w0-blank, or a lamp-lit map's own blank with its lamps. It runs identical code in both arms, so its ratio is that map's noise floor, and it is the assets-only reference at the same camera.
- **Pixels.** SwiftShader is deterministic: a repeat of the same arm is byte-identical, which the editor mode checks. GPU frames are not (they vary between runs of one tree), so pixels are compared on SwiftShader only. Each capture comes with a depth-tie mask: the frame drawn again with strict `<` instead of the default `<=`. Pixels that change are where draw order decides between surfaces at equal depth. A differing pixel is explained only if it is such a tie in either arm, and the share of unchanged pixels that are ties is reported as the control.
- **Triangle-bound proxy.** SwiftShader rasterises on the CPU, so its paired whole-frame times weigh triangles and fragments far more than draws. It stands in for a GPU-bound device, such as a phone, on the maps whose triangles a change moves: repeated designs and the lamp-lit Gross district.
- **Assets only.** `--assets-only` times each view again with every mesh outside the asset layers hidden while the frame renders (round 2's direct method): placed prefab copies and their instances, the wall group, roof models and their merge stay; everything else is hidden. Such a frame is the asset layers plus the frame's fixed passes and its per-frame scene updates (lights, daylight, biomes, scenery), which isolation does not skip. Both arms carry the same of these, so the ratio is a lower bound on the assets' own speedup where costs add; where a change trades CPU work for GPU work, its GPU time can hide behind the inherited CPU work, so read it with the GPU time beside it, and the whole frame as what the user sees. The run is refused unless, for every run, map, view and arm, the isolated frame's draws minus an all-hidden frame equal the whole frame's draws minus the blank map's at the same camera, exactly (calls, shadow calls and triangles). The close and far views sit at each map's buildings, so the reference blank is counted once at those cameras too. The older figure, the frame minus the same run's blank-map frame, is kept as `estimateBySubtraction` with its per-run range, for the overview and the cutaway only; below the blank map's own spread it means little. Round 1's record subtracted the blank map's own close view, a different camera; those close-view figures are withdrawn.
- **Exact counts, headless.** `tests/asset-draw-counts.test.mjs` pins the asset layers' draws for every unlit workload and the editor's two level states (`tools/asset-draw-counts.mjs` constructs the editor's own scene classes on a headless stand-in for the AFT scene, drives them as the editor does, opening the map and setting each view with `setOptions`, and counts what the renderer issues, culling off). `--expect` checks that the candidate's frames issue exactly those counts with culling off on the asset meshes, and prints how many headless and culled counts it compared. The bench's cutaway, too, goes through `setOptions` and waits for the prefab update that it starts.
- **Exact counts, culled.** `tests/fixtures/asset-culled-counts.json` pins, for every map (lamp-lit ones included) and view, the asset layers' draws as the candidate's frames draw them: culled by the view, the sun's shadow camera and every lamp face, through as many light passes as the light renderer needs. So a culling or bounds change, or more triangles under lamps, changes them. They hold for the browser capabilities that decide them (WEBGL_multi_draw, the texture units) and a fixed 1056 × 916 canvas, which the fixture records; another rig is refused, not compared. `--counts-only --expect` checks both fixtures without rasterising; `--write-culled` re-pins this one after a reviewed change. CI runs it as `npm run review:asset-counts` in Chromium with software WebGL.
- **Pixels** are a review step, not a CI gate. Repeated designs round differently from separate meshes, so a pixel gate needs a tolerance, and committed reference frames would pin the CI browser's SwiftShader build; the culled counts already see a copy or roof culled wrongly. The SwiftShader comparison of both trees, with its tie masks, is the review for any change to the counts.
- **Served files.** Every response is hashed; each arm's served-file digest names exactly what it ran.

## Running

```text
npm run build                                   # in each tree whose editor is measured
node tools/bench/workloads.mjs                  # writes artifacts/bench/maps/
node tools/bench-asset-rendering.mjs --editor --a <baseline tree> --runs 4 --backend gpu --assets-only --expect
node tools/bench-asset-rendering.mjs --editor --a <baseline tree> --runs 2 --backend swiftshader
node tools/bench-asset-rendering.mjs --editor --counts-only --backend swiftshader --expect   # npm run review:asset-counts
node tools/bench-asset-rendering.mjs --diff --explain --a <baseline tree>
node tools/bench-asset-rendering.mjs --node --a <baseline tree> --runs 8
```

`--b` defaults to this checkout. Results go to `artifacts/bench/` (ignored). The scripts find Playwright the way `tools/art-review-browser.mjs` does, and close their browser and server in a `finally`. Timings name their rig; compare arms only within one run of the tool.

The first full run measured the answer to round 1, recorded in [the round-1 review](reviews/2026-10-29-hostile-review-0.8-round-1.md#the-answer-to-round-1-measured). That run was the editor mode on an RTX 3080, with 6 paired runs, against main `f6caeef`. At the overview:

- **The GPU timer** exceeds the CPU's submit time (`own`) only on walls: the candidate's free-angle walls and both arms' axis-aligned walls. Everywhere else both arms are fed slower than they draw, so the span's ratio is the feed's.

- **Against per-copy batches** (the candidate with `instancing: false`, 4 runs), the batched clusters are faster unlit: ×1.07–2.06 for 32 copies, ×1.00–1.30 for rows of eight. Lit by six fires they are ×0.86–1.21 and ×0.82–1.03, slower in the close and far views. The null controls are ×0.87–1.03.
