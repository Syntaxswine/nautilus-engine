## Minimal normal editor flow

1. **Discover through the existing palette composition.** Read `GRENADE_COMPONENT` once from the public entry and show its profile, guide, candidate status and support limits. Keep it separate from the actor's visual weapon selection. Until a reviewed typed authoring recipe exists, its Use action reports that binding is unavailable; the editor must not advertise functional placement from metadata alone. Do not pass the descriptor to `discoverPartDefinitions` or invent a placeable solid with grenade behavior hidden in it.
2. **Use a typed actor/loadout binding.** For this first profile, Use targets an explicitly selected compatible actor/loadout, rather than dropping a world pickup. Inspector choices are the fixed profile and bounded integer starting stock, defaulting to the published 3 only when creating new authoring. Existing live stock is never initialized from that default. Costs, range, blast and damage remain the selected source profile's rules, not arbitrary inspector tuning. World pickups, other owners and unsupported cast/control selection remain unavailable until separately implemented.
3. **Compile and record one authoring transaction.** Coder's accepted public contract must serialize the binding, validate its owner, generate stable source targets and derive item requirements alongside actual parts requirements. Place/configure/copy/delete each submits one complete candidate to the editor journal. Copy allocates fresh authored identities and remaps internal owner links under the declared external-link policy; it does not copy runtime throw receipts. Failed/stale preparation retains accepted authoring, redo and preview. Missing bindings select the real actor/loadout/property through public source diagnostics.
4. **Check the complete selected scene/profile.** Use `partsRequirements`/`assertPartsCompatible` for a compiled parts scene and `grenadeRequirements`/`assertGrenadeCompatible` for its valid grenade host projection. The required services are `atomic-grenade-context-commit-v1`, `farmyard-visibility-refresh-v1` and `farmyard-body-registration-v1`. Aim input is optional to headless play; the selected UI player must declare its own input/presentation needs. Capability declarations alone do not install any service.
5. **Mount the reviewed shared player/binder.** Bind the standard grenade module to the retained game context once. UI uses public preview/stage/aim and the architect's fixed native provider. A newly staged throw is committed only after comparing both `expected.state` and freshly projected `expected.context`, with host inventory/HP/AP/fog/control/consequences stored atomically. Only then present the returned sequence. Animation callbacks, cancellation, retries, authoring reload and visual failure cannot create another attack or refund a committed one. No per-map action code or second interaction kernel is needed.

The ordinary core already stages guard sight, detection/fog, control and eligible AP transitions inside atomic `next`. The host visibility binding applies those accepted facts while retaining the complete game state. It must not rerun engagement/refill policy or grant AP a second time. Preserve unrelated actor/game fields when applying deltas by stable identity.

## Narrow shared work needed before step 2 can enable

**Coder/architect:** settle a versioned typed actor-loadout authoring binding, its discovery descriptor, profile/default validation, explicit owner reference/copy policy, source map and content-derived requirements. A small companion authoring envelope consumed by the shared compiler is a provisional minimal choice; the exact shape/version and whether it belongs in a later parts profile are their decision. Do not smuggle stock/profile/owner fields into closed parts-v1, door initial overrides, numeric parameters, strict world-v1 or portable legacy maps.

**Core/retained host:** accept and test the complete geometry/context adapter. Grenade actor `z=0` is a layer constraint, trajectory `z` is height above ground, and native parts `h` is metre elevation. Parts slabs can extend below zero; grenade boxes accept nonnegative `z0` and store their upper height bound separately. Current dynamic door leaves and grenade-specific walking/flight/blast roles also require deliberate projection. Do not clamp negative geometry, treat every render box as a blast wall, omit closed/open leaves, crop obstacles or equate a floor index with metres. The frozen Farmyard projection remains the available adapter for its exact retained source profile.

**Profile boundary:** this grenade candidate refuses windows/glass, fuel/volatile targets, active fire and other floors before costs. The ordinary profile reads no RNG; fueled/reactive RNG contexts remain refused. Derive feature presence from the complete host/authored context; never fill support flags with `false` to conceal unsupported content. The two-story functional-parts proof therefore cannot serve as this profile's grenade acceptance scene. Use a separate compatible planar, nonreactive scene, preserving unsupported authoring with explicit diagnostics and refusal.

**Persistence boundary:** starting-stock authoring is distinct from the live grenade checkpoint. Restore through `openGrenadeState` without refilling or replaying presentation. Reproject the latest complete host context only at a grenade-action/durable-save boundary and check `matchesGrenadeContext`. If it is exactly unchanged, create no new context checkpoint. If it changed, stage `adoptGrenadeContext` with a new durable checkpoint ID and current expected revision, retaining the complete host and sidecar atomically. Do not checkpoint movement/render ticks.

**Strict limits and refusal:** every newly accepted `adoptGrenadeContext` consumes another durable record, just as a new throw does. Checkpointing cannot compact or reset the strict 128 combined-record limit. Full-world bounds, the aggregate 500,000-node/8,000,000-UTF-8-byte budgets and composition limits can be reached before record 128. Parts runtime `hostData` is capped at 1,000,000 bytes, so embedding an otherwise valid grenade checkpoint is not automatically valid. Validate the complete prospective bundle before an action or changed-context save is accepted. If it cannot fit, refuse that operation with the concrete public diagnostic (for example `JOURNAL_LIMIT` or `STATE_LIMIT`), preserve the last accepted state/save and spend nothing. Serializing an unchanged valid checkpoint needs no new receipt. Continuing beyond a bound requires a future explicitly reviewed archival/migration policy preserving deduplication; never start a fresh sidecar, reset IDs or drop old receipts to evade the limit.

## Acceptance and recommendation

After the architect distributes the combined fixed dependencies, prove discovery -> selected actor/loadout -> one accepted configuration transaction -> authoring save/reload -> compatible shared player in two planar scenes. Exercise a transformed/copy instance, fresh IDs/internal links, zero/default/custom stock, absent owner/service, optional aim, unsupported windows/two-story content, legacy refusal, failed/stale compilation and preserved undo/redo. Restore spent/injured runtime values; confirm no refill or effect replay, duplicate/stale commands have no second cost, and host changes between preview/commit reject. Check that unchanged-context saves add no receipt, changed-context adoption consumes one, and both record exhaustion and an earlier full-world/node/byte failure refuse an action or changed-context save without losing the previous bundle. Confirm host visibility applies staged AP/control/fog once and fueled contexts refuse without an ordinary-core RNG read. UI's real native animation/provider and phone/desktop review remain their existing acceptance work.

Prefer typed actor-loadout authoring with the shared source profile for this increment. **Accuracy:** it represents the candidate's inventory and command-time effects explicitly; there is no implemented ground-pickup/fuse behavior to imply. **Efficiency:** reuse existing compiler/requirement and module calls; costs have not been measured here. **Narrative:** Farmyard retains its stock, equipment-sensitive AP and ordinary consequences, while richer Tinderbox/window/fire behavior requires its own reviewed profile. No implementation or consumer pin is changed by this plan.
