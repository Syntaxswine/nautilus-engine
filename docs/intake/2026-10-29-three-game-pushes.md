## Farmyard pane integration and guard visibility

**Source:** released main `251bf8094b5f9ebe44208443084c1a6d6658512a`, including window integration `3c29604bdfb4210864910369ec09c59095249e8a` and guard correction `7f722bc00ba985d3ef95db593b1756a0564de4db`. This materially updates `FC-0ef5b71-industrial-windows` and `FC-68c10c4-pane-breaks` from the [earlier report](2026-10-29-window-panes-and-administration.md).

`sites/tactical-animal/dist/art/windows/{catalog.js,catalog.json,geometry.js}` now provides 39 presets plus `window.full.borderless`, with explicit metre `{width,height}`. `window-{system,authoring,view,shatter,editor-controls,editor-buffers}.js` connects pane identity, editor dimensions/history, real impacts, saved breakage, bounded effects and iframe buffer ownership. `dist/solo-game.js` and `tests/guard-window-integration.test.mjs` correct guard approach/stand-in visibility through real apertures instead of wall envelopes. Tall glass grants no upper-floor walking or broken-window vaulting.

**Accuracy:** prefer actual panes, mullions and sill heights over an opaque wall box for sight, targeting and authoring. Keep Farmyard's first-hit-stops-and-breaks policy as a named tactical profile: real projectiles can penetrate glass, so it is not a universal physical material law. Cosmetic shards use 7.8 m/s² gravity and a flat receiving floor at zero; they are not general falling-body physics. Tinderbox should retain separate heat, fuel and material decisions.

**Efficiency:** prefer bounded analytic cosmetic fracture for phone tactics: six live meshes/210 triangles, at most 70 per sheet and three audio voices are source limits, not measured frame rates. A 20 × 10.6 m sheet remains one pane. Exact aperture tests add local work but avoid false occlusion; use candidate filtering rather than general rigid-body shards.

**Narrative:** prefer the full-sheet/divided-pane distinction and once-only break cues for readable tactical consequences. Native glass and frame geometry also suit exposition architecture. Heat-driven cracking, falling hazards and traversal require separate game policies rather than inheriting the visual effect's limits.

**Assignments / acceptance:** Coder owns immutable closure, pane state/receipts and optional query adapters; Artist reviews all rotations, seams, tall shard landing and native material output; Editor owns metre/storey controls, history and serialization; UI audits labels, disabled frame finish, phone layout and recovery. Preserve legacy saves and explicit unsupported-feature refusals. Check confirmed impact versus preview, burst-through-hole, independent instances, save/revisit without replay, undo/redo/import and cross-realm buffers. Keep original shatter study pin `ebf51393909040b61a7c40649d9d5f0ac3678735`, CC0 recording/license and Three notices.

The donor's final native WebGL workflow [passed at the exact window commit](https://github.com/Syntaxswine/farmyard-commando/actions/runs/40899381853). Older README paragraphs still say the gate is pending; the successful final run supersedes that checkpoint, without proving physical speaker playback or Nautilus acceptance.

## Tinderbox exact-target doors and input recovery

**Source:** published `dc7f537a83a7e832a0dfa0757d0b2700b909c053`; review roots are `src/runtime/{navigation,camera,index,door-labels,sections}.js`, `src/ui/{index,door-action,model}.js`, and the contextual-door/movement handoffs and tests listed in the evidence manifest.

The interaction snapshot identifies the exact door and desired Open/Close action, human label, reason and world anchor. Commit revalidates target, reach, floor, occlusion, readiness and destination-leaf occupancy. A stale request cannot operate a newly nearer door; repeated Open does not Close. Camera projection accounts for actual UI-root offsets/clipping. Joystick gestures retain their press-time rectangle and recover from missed mouse/pen release, no-buttons hover and a fresh mouse press.

**Accuracy:** prefer explicit target/state plus current geometry checks for intentional operation of a particular door. Destination-pose occupancy is useful but does not establish continuous hinge-sweep safety for an animated door; compare Farmyard's current door work before choosing that shared capability. Input changes improve control fidelity, not physical movement realism. Tinderbox's requested 9 m/s speed is game tuning, not a shared realistic speed default.

**Efficiency:** prefer one anchored gesture rectangle and the existing camera transform over repeated layout reinterpretation or another camera service. These are code-based cost estimates; there is no new input latency or frame-time measurement. Exact source triangles belong behind the host geometry seam.

**Narrative:** prefer a visible action attached to the selected door and an explicit blocked-close reason: player intent remains readable during movement, pause and obstruction. Retain Farmyard's UI direction while sharing the action contract, not Tinderbox's complete HUD or movement balance.

**Assignments / acceptance:** Architect folds the comparison into active door/functional-parts work. Coder owns a strict, headless action snapshot/commit boundary; UI owns native button/keyboard/pointer lifecycle and camera-to-root presentation; Editor consumes the reviewed contract; Artist only checks anchor/leaf geometry if needed. Test stale/unknown targets, repeated requests, occupied poses, unloaded sections, no simulation-time advance during projection, resize/scroll, focus/pause/cancel/dispose and missed release. Ship a public connection example and controls proof at desktop/phone sizes. Existing donor browser evidence used actual navigation and production controls with an SVG plan; it does not certify whole-map WebGL interiors.
