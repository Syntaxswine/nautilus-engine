[Published source](https://github.com/Syntaxswine/tinderbox/tree/d5b43dd5446d93dd263d1234e12ed1551743de56/src/simulation)

- **Accuracy.** Prefer immutable publication when simulation mutation and publication revisions are explicit. It retains the same fuel, heat, ordering and renderer inputs without introducing a second simulation. The donor tests cover retained snapshots, exact row-major fuel totals, retreating fire fronts and mutable custom obstacle metadata. Those are behavioral controls, with no new physical calibration.
- **Efficiency.** By code inspection, unchanged publications avoid record allocation and repeated classification or GPU field uploads. A changed field can still copy its complete array, and readers can still traverse the array. Cost depends on field size and change density. The obstacle publisher relies on its host's replacement rules and a particular in-place height change. It requires a complete invalidation contract before reuse with general engine geometry. No scout CPU or allocation benchmark was run.
- **Narrative.** Subjectively prefer a shared publication boundary for Tinderbox's detailed fire and multi-view diagnostics because visible effects can read one confirmed world state. Tactical consumers benefit only where their update volume justifies caching. Preserve the chosen game's fire policy and appearance while sharing publication ownership.

**Compatibility and dependencies.** This is architecture, with optional 2D field textures and existing 3D presenters as consumers. It introduces no model, rig, material or collision content. Bind to a host revision or explicit dirty set, including doors, destruction, map replacement and custom mutable records. Keep authoritative geometry and save transactions with their current owner. Serialize full durable values through existing save APIs. Frozen JS identity and cached renderer lists are temporary runtime state.

**Suggested work and effort estimate.** Coder can apply the pattern inside the bounded finite-heat assignment `TB-7ba7487-finite-heat` after its state and geometry contract is selected, estimated 1–2 builder days. Use the existing publication layer in that implementation if one already exists. Artist/UI review the affected field, flame and ground views together only when the extraction reaches a playable host.

**Accept when.** Retained snapshots cannot change after a step, reset or reload. Unchanged records can reuse identity, and every advertised change invalidates its dependent view. Mutable custom data receives detached handling. Equivalent fixed-tick replays preserve state, event order and resource totals. Door/fragment retirement cannot leave stale occlusion or fire. Measure quiet, sparse-change and dense-change scenes, and compare separate CPU allocation and GPU-upload costs.
